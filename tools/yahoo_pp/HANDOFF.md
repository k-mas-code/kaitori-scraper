作成日：2026-10-30

目的：同じ店舗リストを、WSL上のスクリプト（Claude Code など）だけで再取得できるようにする。

## 1. 何を作っていたか

Yahoo!ショッピングの「プロモーションパッケージ（PP）加入ストア」の一覧を、5ジャンルについて作成した。

PP加入ストアの公式一覧は存在しない。代わりに **ボーナスストアPlus（BSPlus）の参加ストア一覧** を使った。BSPlusに参加するには「PP加入＋PRオプション設定」が必要とされているため、BSPlusの参加ストア ≒ PP加入ストア（の一部）とみなせる。

| ジャンル | カテゴリコード |
|---|---|
| スマホ、タブレット、パソコン | 2502 |
| テレビ、オーディオ、カメラ | 2504 |
| 家電 | 2505 |
| ゲーム、おもちゃ | 2511 |
| スポーツ | 2512 |

最終成果物は `yahoo_pp_stores_5genres.xlsx` で、シート構成は次のとおり。

- 概要
- ローテーション分析
- ポイント上乗せ調査
- 全ジャンル
- ジャンル別5シート
- 日別掲載数
- 除外リスト（非適格）

### 処理の流れ（前回の実績件数）

1. BSPlus参加ストアを取得：5ジャンル・74日分（8/16〜10/28）で **1,263店**
2. 掲載スケジュールを作成：日別に +9%枠／+4%枠／不参加 を記録
3. 優良ストアを判定：405店
4. 適格請求書発行事業者で絞り込み：**適格1,011店**、非適格252店は除外リストへ
5. ストア評価を取得：星5〜星1の件数（1,011店）
6. 対象をさらに絞り込み：レビュー300件以上・平均4.5以上で **562店**
7. ストアポイントの上乗せ率を調査（562店）：上乗せありは189店

## 2. WSLでやる場合の前提

- **前回はクラウド環境のシェルからYahooに届かなかった**（プロキシの許可リスト外）。そのため、すべてブラウザ上の `fetch()` で取得した。
- **WSLなら `requests` / `curl` で直接取れる見込み**。ただし未検証なので、まず §3 の各URLを1件ずつ叩いて、ステータスと中身を確認すること。
- ブラウザで取得していたときは、ログインしていない状態のCookieが付いていた。Cookieなしで同じ内容が返るかは **未確認**。うまく取れない場合は、ブラウザと同じ `User-Agent`・`Accept-Language: ja` を付けて試す。それでも駄目なら Playwright（Chromium）で `page.evaluate(fetch)` する。
- 推奨構成：
  - Python 3 ＋ `requests` ＋ `beautifulsoup4`（または `lxml`）＋ `openpyxl`
  - 取得したHTMLやJSONは、URL単位でローカルにキャッシュする（再実行・再開のため）

## 3. データ取得の手順（エンドポイント別）

### 3-1. BSPlus 参加ストア一覧

**ステップA：eventId を集める**

- ページ：`https://shopping.yahoo.co.jp/promotion/campaign/bsplus/list/`
- 1日につき eventId が2つある（+9%枠と+4%枠）。
- このページから、日付ごとの eventId を抜き出す。前回はページ内のリンクと `<select>` から取得した。具体的なHTML構造は再確認が必要。
- 前回カバーできた期間は 8/16〜10/28 の74日。過去分がどこまで残るか、未来分がどこまで公開されているかは、その時点で確認すること。

**ステップB：日付×ジャンル×枠ごとにストア一覧を取る**

- `POST https://shopping.yahoo.co.jp/promotion/campaign/buybuy/api/acstores/`
- Body（JSON）：`{"eventId": <eventId>, "campaignType": "point", "category": "<2502等>"}`
- レスポンスは **HTML断片**。中のストアリンク `store.shopping.yahoo.co.jp/<storeId>/` から、ストアIDとストア名を抜き出す。
- **枠の見分け方**：同じ日付の eventId 2つのうち、ストア総数が少ない方が +9%枠、多い方が +4%枠。
- **件数の検証**：一覧ページのセレクトボックスに件数が表示されている。前回は「74日×5ジャンル×2枠」すべてで、取得件数と表示件数が一致した。再取得時も同じ照合を入れること。
- 1ストアが複数ジャンルに出ることは、前回はなかった。

**出力：スケジュール文字列**

- ストアごとに、日付順の74文字の文字列で持つ。各文字は `9`（+9%枠）、`4`（+4%枠）、`-`（不参加）。
- 前回のファイル `sched.json` の形式は `{storeId: [カテゴリコード, "974-…"]}`。

### 3-2. 優良ストア判定

- 1店につき、店内検索 `https://store.shopping.yahoo.co.jp/<id>/search.html` の先頭商品を1件開く。
- 商品ページHTMLに `excellentStoreGold_logo`（金色の「優良ストア」バッジ）があれば優良ストア。
- ストアトップページは、独自トップを使っている店で geocities 側にリダイレクトされるため、判定に使わないこと。
- 優良ストアの判定は毎月見直されるので、月が変われば取り直す。

### 3-3. 適格請求書発行事業者の判定

- `GET https://store.shopping.yahoo.co.jp/<id>/info.html`（会社概要ページ）
- 判定は2通りあり、前回は全店で結果が一致した。
  1. HTML内の埋め込みJSON：`"bcpf":{"registrationNo":"T1234567890123"}` → 番号があれば適格。非適格の店は `null`。
  2. 備考欄のテキスト：「当店は、適格請求書発行事業者です。」なら適格、「…ではありません。」なら非適格。
- 正規表現の例：`"bcpf":\{"registrationNo":"?([^"},]*)"?\}`
- 前回の結果：適格1,011店、非適格252店。どちらの表記もない店は0店。

### 3-4. ストア評価（星別件数）

- `GET https://shopping.yahoo.co.jp/store_rating/<id>/store/review/`
  - ホストは `shopping.yahoo.co.jp`。`store.shopping` ではない点に注意。
- ページのテキストに「星5つ 163,620件」「星4つ …」のような形で件数が出る。
  - 正規表現の例：`星([1-5])つ\s*([\d,]+)件`
- 平均評価は表示値（例 4.62）があるが、レビューが少ない店では表示されない。**5つの件数から計算するのが確実**。
- 2014/1/22 より前のレビューは含まれない（ページ上の注記）。

### 3-5. ストアポイント上乗せ率

**① 店内検索ページで、上位30商品の付与率を取る**

- `GET https://store.shopping.yahoo.co.jp/<id>/search.html`（おすすめ順の先頭30商品）
- `<script id="__NEXT_DATA__">` のJSONを再帰的にたどる。`url` に `/<id>/` を含み、`point.rate`（数値）を持つオブジェクトが商品にあたる。
- 商品コード：`url` の末尾 `<code>.html` から取る。
- `point.rate` は「エントリー込みの合計付与率」（`totalRatioWithEntry` と同じ値）。

**② 商品ページで、上乗せ分を確認する**

- `GET https://store.shopping.yahoo.co.jp/<id>/<code>.html` の `__NEXT_DATA__` → `props.pageProps.point`
  - `totalPointRatio`：エントリーなしの合計
  - `currentCampaignList[].partsCampaignList[]`：`{title, ratio}`。標準は PayPay残高 0.5 ＋ ストアポイント 1 ＋ LINE連携 2.5 ＝ 4
  - `conditionalCampaignList[].partsCampaignList[]`：エントリーが必要な特典（例：「プレミアムな日曜日 ＋5％」「ボーナスストアPlus ＋4％ / ＋9％」「LYPプレミアム ＋2%」）
- **上乗せ率 ＝ `totalPointRatio` − Σ`currentCampaignList` の ratio**
  - 画面上の内訳では「この商品のポイントUP分 → ストアポイント上乗せ分 ○%」として表示される。
  - 注意：パーツ一覧（`partsCampaignList`）は商品ごとではなく店舗共通の内容になっている。上乗せ分はこの一覧には出てこないので、必ず上の差分で計算する。

**③ 一覧の率の分解（商品ページを開かずに済ませる方法）**

一覧の率は次のように分解できる。

一覧の率 ＝ 基本4 ＋ 上乗せ ＋ BSPlus枠（その日の 0 / 4 / 9）＋ 日曜特典5（BONUS対象商品だけ）

- BSPlus枠は §3-1 のスケジュールから分かる。
- **日曜以外**（かつ5のつく日以外）なら日曜特典は入らないので、上乗せ ＝ 一覧の率 − 4 − BSPlus枠。店内検索1回で30商品分が決まり、1店1リクエストで済む。
- **日曜**は、差分が5以上の率だと「上乗せ」と「日曜+5」の区別がつかない。前回はその率の商品だけ商品ページを開いて確認した（1店あたり最大3つまで）。
- 例外：
  - 率が 6.5 や 2.5 の商品がある。LINE連携の対象外などで基本が 2.5 になる商品で、上乗せは 0 と扱った。
  - BSPlus枠が付かない商品もある（付与上限などが理由と思われる）。

## 4. アクセス頻度の制限（重要）

- **短時間に大量にアクセスすると HTTP 489（「ページは現在表示できません」）が返る。**
  - 前回は、間隔をあけずに約600リクエストを送ったところで発生した。
- その後の設定では、数千リクエスト送っても一度も発生しなかった。
  - **1並列・リクエスト間隔2.2〜2.5秒**（およそ20〜25件/分）
  - **489を受け取ったら即座に停止**し、時間をおいてから、途中の続きから再開する
- 所要時間の目安（この間隔の場合）：

| 作業 | 店舗数 | 所要時間 |
|---|---|---|
| 会社概要の確認 | 1,263店 | 約1時間 |
| 評価ページの取得 | 1,011店 | 約40分 |
| 上乗せ調査（日曜・商品ページ併用） | 562店 | 約80分 |
| 上乗せ調査（平日・一覧のみ） | 1,011店 | 約40分（見込み） |

- 実装上の注意：
  - 進捗（処理済みのストアID）をファイルに保存して、途中から再開できるようにする。
  - 取得したHTMLはキャッシュし、同じURLを二度叩かない。

## 5. 既知の落とし穴

- 日付の境界は JST。タイムスタンプは epoch 秒（例：1791039600 ＝ 2026-10-04 00:00 JST）。
- 「休み日」ローテーション：最も多い掲載パターン（189店が完全に同じ）の不参加日28日を「休み日」と定義した。
  - 休み日は、日曜・5のつく日・1日・BSPlusの「さらに+2%」の日と一度も重ならなかった。
  - 11月以降も同じ周期かは未確認。
- BSPlusの「さらに+2%／+3%（優良）」の日：
  - 9月分はキャンペーンページから取得した。
  - 10月分は社内限定カレンダーの画像から（10/2, 7, 16, 20, 27, 28）。
  - 8月分は未確認。
- 一覧ページのポイント率は、ログインなしで見たときの値。上乗せ率自体はログインの有無で変わらないはずだが、未検証。
- Excel出力：日付は date 型で書く。`+9` のような文字列にすると、Googleスプレッドシートが数値に変換してしまう。
- Driveにxlsxのまま置くと、Googleスプレッドシートには変換されず、Office互換モードで開かれる。

## 8. WSLでの実装タスク（提案）

1. `probe.py`：§3 の各URLを1件ずつ取得して、ステータスと抽出結果を表示する。Cookieが必要かどうかもここで判断する。
2. `bsplus_fetch.py`：eventId を収集し、acstores API を呼んで `sched.json` を作る。件数の照合も入れる。
3. `enrich.py`：ストアIDごとに info（適格）、評価、優良、上乗せを順に取得する。間隔2.5秒・489で停止・途中再開に対応する。
4. `build_xlsx.py`：前回の `build_xlsx3.py` と同じ構成でExcelを出力する（前回の生成スクリプトは別途共有可）。
5. 定期実行する場合は、BSPlusの予定が更新されるタイミング（月初・月中）に合わせる。
   - 上乗せ調査は **日曜と5のつく日を避けた平日** に回す。
